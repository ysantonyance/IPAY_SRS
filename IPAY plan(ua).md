## 1. Вступ

### 1.1. Мета документа

Цей документ визначає функціональні та нефункціональні вимоги до веб-платформи **Amazon Clone (IPAY)** — системи електронної комерції, розробленої в рамках курсового командного проєкту з дисципліни ASP.NET Core. Версія 1.1 відображає **фактичний стан реалізації** і слугує єдиним джерелом правди для команди розробки, QA та керівництва на етапах реалізації (Scrum-спринти), тестування (NUnit), документування (Scalar/OpenAPI, Doxygen) та захисту.

### 1.2. Обсяг продукту

IPAY — веб-платформа електронної комерції, що дозволяє користувачам переглядати товари, формувати кошик, оформлювати замовлення з (імітованою) онлайн-оплатою та оцінювати товари. Продавці керують власними товарами, модератори й адміністратори — каталогом, замовленнями, заявками на статус продавця та користувачами. Додатково платформа містить відеокаталог (серіали, епізоди, жанри) з імпортом метаданих з OMDb. Проєкт реалізується як **командний проєкт** із застосуванням Scrum, Git та архітектури Clean / Onion.

### 1.3. Аудиторія документа

Команда розробників (Backend, Frontend, Full-stack), керівник проєкту, члени комісії з захисту, QA-інженери (в рамках навчального процесу).

## 2. Загальний опис

### 2.1. Перспектива продукту

IPAY розробляється як самостійний навчальний продукт з нуля; архітектурні та UX-рішення базуються на практиках сучасних e-commerce платформ (візуальний стиль наслідує Amazon). Система складається з клієнтської частини (React SPA), серверної частини (ASP.NET Core Web API) та шару даних (Google Cloud Firestore). Автентифікація поєднує власні JWT-токени з Firebase Authentication (вхід через Google, підтвердження email, лист скидання пароля).

### 2.2. Класи користувачів та привілеї

| Роль | Опис | Ключові дозволи |
|---|---|---|
| Гість (Guest) | Неавторизований відвідувач (опційно з гостьовою сесією) | Перегляд каталогу, пошук, фільтрація, сортування, деталі товару, кошик у localStorage |
| Покупець (Customer) | Авторизований користувач | Серверний кошик, оформлення та скасування замовлень, історія, оцінки та відгуки, профіль, подання заявки на статус продавця |
| Продавець (Seller) | Покупець зі схваленою заявкою | Усе, що Customer, + створення/редагування/видалення **лише власних** товарів, завантаження зображень |
| Модератор (Moderator) | Співробітник платформи | Керування товарами, категоріями, виробниками, замовленнями, відеокаталогом; перегляд користувачів; блокування/розблокування користувачів (крім адмінів і модераторів); призначення/зняття ролі Seller; розгляд заявок продавців |
| Адміністратор (Admin) | Менеджер платформи | Усе, що Moderator, + призначення/зняття ролі Moderator, CRUD користувачів і гостей; **ніхто не може бути зроблений адміністратором через API** |
| Система | Автоматизовані процеси | Перевірка ролі в JWT на кожен запит, ротація refresh-токенів, відправлення email-листів |

> **Зміни проти v1.0:** додано роль Moderator; роль «Продавець (Персональне/Бізнес)» уточнено — поділу на персональний/бізнес тип у реалізації немає; «Система» більше не виконує модерацію, архівацію та очищення кошика.

### 2.3. Операційне середовище

| Компонент | Специфікація (фактична) |
|---|---|
| Клієнт | Браузери Chrome, Firefox, Safari, Edge (2 останні версії); адаптивний UI (Tailwind CSS 4) |
| Сервер | ASP.NET Core на **.NET 10**; Docker-образ (порт 10000), хостинг **Render** |
| Клієнтський фреймворк | **React 19.2**, Vite 8, React Router 7, Axios, Tailwind CSS 4, Firebase JS SDK 12 |
| Серверний фреймворк | ASP.NET Core Web API (controllers), JWT Bearer, політики авторизації |
| База даних | **Google Cloud Firestore** (основне сховище; одна колекція на сутність) |
| Доступ до даних | Власний `FirestoreRepository<TEntity, TDocument>` + *Document*-класи для мапінгу |
| Автентифікація | JWT + refresh-токени (власні), Firebase Authentication (Google, підтвердження email, скидання пароля) |
| Зображення | Cloudinary (CDN) |
| Email | SMTP (MailKit) |
| Зовнішні дані | OMDb API (відеокаталог) |
| Архітектура | Clean / Onion: `Domain` → `Application` → `Infrastructure` → `WebApi` |
| Мови інтерфейсу | Англійська (en), Українська (ua), Російська (ru) |

### 2.4. Обмеження дизайну та реалізації

| Шар | Технологія | Обґрунтування |
|---|---|---|
| Frontend | React 19.2 + Vite + Tailwind | Компонентний підхід, швидка збірка, утилітарні стилі |
| Backend | ASP.NET Core Web API (.NET 10) | Кросплатформеність, DI, політики авторизації |
| Валідація / мапінг | FluentValidation 12, AutoMapper 12 | Декларативні правила; ізоляція DTO від доменних сутностей |
| БД | Firestore | Серверless, не потребує адміністрування; real-time можливості SDK |
| Auth | JWT Bearer + Firebase Authentication | Stateless API; делегування Google-входу, верифікації email і скидання пароля Firebase |
| Документація API | Swagger UI (лише Development) + Scalar registry | Автогенерація з OpenAPI; публічний довідник |

| Документація коду | Doxygen | Публічний сайт із XML-коментарів |

> **Відхилення від v1.0:** ASP.NET Core Identity, EF Core / SQL Server, DocFX, SignalR та Elasticsearch у проєкті **не використовуються**. Усі відповідні вимоги переформульовано під Firestore (див. розділ 6).

### 2.5. Припущення та залежності (Assumptions & Dependencies)

| № | Опис | Тип | Вплив у разі порушення |
|---|---|---|---|
| A-01 | Команда використовує Git (GitHub) із feature-branch workflow та Pull Request reviews | Внутрішня | Порушення контролю версій, складнощі зі звітом |
| A-02 | Реальний платіжний провайдер (LiqPay/Fondy/Stripe) у поточній версії **не підключений**; використовується `MockPaymentProvider` | Зовнішня | Оплата лише імітується (FR-10) |

## 3. Межі проєкту

### 3.1. У межах проєкту (In Scope)

- Каталог, кошик, замовлення, імітована оплата, адмін-панель
- Реєстрація, автентифікація (email+пароль, Google), 2FA через email, авторизація на ролях (Customer, Seller, Moderator, Admin)
- Заявки на статус продавця; кабінет продавця для власних товарів
- Оцінки товарів (1–5 зірок) та текстові відгуки
- Фільтрація, сортування та курсорна пагінація товарів
- Відеокаталог: серіали, епізоди, жанри, імпорт з OMDb
- Адміністративна панель: товари, категорії, виробники, медіа, замовлення, заявки продавців, користувачі
- Адаптивний UI, інтернаціоналізація (en / ua / ru)
- Unit- та інтеграційні тести (NUnit) бізнес-логіки й контролерів
- Документація API (Swagger/Scalar) та кодова документація (Doxygen), User Guide
- Деплой на Render (Docker для backend)

### 3.2. Поза межами проєкту (Out of Scope)

- Нативні мобільні застосунки (iOS/Android)
- Власний платіжний шлюз (еквайринг) та, у поточній версії, реальна інтеграція з провайдером
- ML-рекомендації товарів
- Інтеграція зі службами доставки (Nova Poshta API) — лише статуси замовлення
- Мікросервісна архітектура — використовується модульний моноліт
- **Відкладено (не реалізовано):** Wishlist, push/real-time-сповіщення (SignalR), аналітичний дашборд, Elasticsearch, окремі описи товарів та складські залишки (SKU), аватар користувача, ієрархія категорій

## 4. Функціональні вимоги

*Формат: **[Пріоритет MoSCoW]** ID — Опис → Критерій прийняття (AC) · Статус реалізації*

### 4.1. Авторизація та реєстрація

**[Must] FR-01** — Реєстрація користувача через email + пароль або Google (через Firebase Authentication). ✅
→ *AC:* Ім'я 2–50 символів (літери, пробіл, дефіс); пароль ≥ 8 символів, з великою і малою літерою, цифрою та спецсимволом; підтвердження пароля; email ≤ 100 символів і унікальний; підтвердження email через Firebase (`Firebase:RequireEmailVerification`); для Google-входу email вважається підтвердженим; валідація через FluentValidation (`RegisterValidator`).

**[Must] FR-02** — Авторизація з розподілом ролей (Guest / Customer / Seller / Moderator / Admin). ✅
→ *AC:* JWT (HS256) містить claims `NameIdentifier`, `Email`, `Role`; термін життя access-токена налаштовується (`Jwt:AccessTokenMinutes`, за замовчуванням 20 хв); доступ до ендпоінтів захищений політиками (`AdminOnly`, `ModeratorOnly`, `ModeratorOrAdmin`, `SellerOnly`, `CustomerOnly`, `RegisteredUser`, `AnyAuthenticated`, `NotBanned`); заблокований користувач не проходить політики з `NotBanned`.

**[Must] FR-03** — Відновлення пароля через email. ✅
→ *AC:* `POST /api/auth/password-reset/start` завжди повертає 204 (не розкриває існування акаунта); лист зі скиданням надсилає Firebase; `POST /api/auth/password-reset/confirm` приймає Firebase ID-токен і новий пароль; помилка повертається як 400 (не 401).

### 4.2. Каталог товарів

**[Must] FR-04** — Перегляд списку товарів з пагінацією (за замовчуванням 12 на сторінку). ✅
→ *AC:* Курсорна server-side пагінація (`limit`, `lastDocId`) на рівні запиту до Firestore; також доступний `GET /api/products/all`. *Примітка: пагінація курсорна, а не за номером сторінки.*

**[Must] FR-05** — Перегляд деталей товару. 🟡
→ *AC:* Відображаються назва, ціна, ціна зі знижкою (фінальна ціна = знижена, якщо `0 < DiscountedPrice < Price`), зображення, виробник, категорія, рейтинг і кількість оцінок, продавець. *Не реалізовано: окреме поле опису, галерея до 5 фото (наразі одне `ImageUrl`), складський залишок/SKU, блок «пов'язані товари».*

**[Must] FR-06** — Пошук та фільтрація товарів. 🟡
→ *AC:* `GET /api/products/filter` за `categoryId`, `minPrice`/`maxPrice`, `brand` (виробник), `search` (за назвою) з курсорною пагінацією. *Не реалізовано: фільтр за рейтингом; повнотекстовий пошук Elasticsearch.*

**[Should] FR-07** — Сортування товарів. ✅
→ *AC:* `GET /api/products/sort` за `sortBy` = `price` / `rating` / `date` та `sortDir` = `asc` / `desc`, виконується на рівні запиту до БД. *Сортування «популярні» не реалізовано.*

### 4.3. Кошик та оформлення замовлення

**[Must] FR-08** — Додавання/видалення товарів у кошик зі зміною кількості. ✅
→ *AC:* Гість: кошик у `localStorage`; авторизований користувач: кошик у Firestore (`/api/cart`, `/api/cart/items`, `/api/cart/clear`); оновлення кількості без перезавантаження; загальна сума обчислюється на клієнті в реальному часі; кошик очищується після оформлення замовлення.

**[Must] FR-09** — Оформлення замовлення з адресою доставки. 🟡
→ *AC:* Замовлення створюється авторизованим користувачем зі статусом `Pending`; адреса містить країну, місто та вулицю; ціна позиції фіксується на момент замовлення (фінальна ціна товару); `UserId` береться з JWT. *Не реалізовано: збереження ПІБ і телефону в замовленні, списання складських залишків.*

**[Must] FR-10** — Оплата замовлення. 🟡
→ *AC:* `POST /api/payments/create` ініціює оплату замовлення зі статусом `Pending` і повертає `TransactionId` та URL підтвердження; `GET /api/payments/mock/confirm` у разі успіху переводить замовлення в `Paid` (з записом в історію статусів); транзакція з `FAIL` у ідентифікаторі імітує відмову; дані картки не обробляються і не зберігаються. *Реальна інтеграція (LiqPay/Fondy/Stripe) відсутня — працює `MockPaymentProvider` (`Provider = "MockPay"`, валюта UAH); оплата «при отриманні» не реалізована.*

**[Must] FR-11** — Історія замовлень у особистому кабінеті. ✅
→ *AC:* `GET /api/orders/my` повертає замовлення користувача з позиціями; доступна історія зміни статусів (`GET /api/orders/{id}/status-history`: старий/новий статус, час).

**[Should] FR-21** ➕ — Скасування замовлення власником. ✅
→ *AC:* `POST /api/orders/{id}/cancel`: можливе лише для статусів `Pending` / `Paid`; чужі замовлення відповідають 404; після відправлення — 400.

### 4.4. Відгуки та рейтинги

**[Should] FR-12** — Оцінка товару (1–5 зірок) та відгук. 🟡
→ *AC (оцінки):* `POST /api/ratings/{productId}` — одна оцінка від користувача на товар (повторна → 409), заборонено оцінювати власний товар продавця (403), лише `RegisteredUser`; середній рейтинг і кількість оцінок перераховуються автоматично; `GET /api/ratings/mine` повертає оцінки поточного користувача. *(AC відгуків:)* `POST /api/reviews` (автентифіковані ролі, не заблоковані) зберігає оцінку й коментар. *Не реалізовано: обмеження «лише після покупки» та «один відгук на товар».*

**[Should] FR-13** — Перегляд відгуків на сторінці товару. 🟡
→ *AC:* `GET /api/reviews/product/{productId}` — публічний; видалити відгук може автор, модератор або адмін. *Пагінація та сортування відгуків не реалізовані.*

### 4.5. Адміністративна панель

**[Must] FR-14** — CRUD категорій товарів. 🟡
→ *AC:* `GET /api/categories` публічний; створення/редагування/видалення та прив'язка товарів доступні ролям Seller, Admin, Moderator. *Структура категорій плоска (без батьківської/дочірньої ієрархії); заборона видалення непорожньої категорії не підтверджена.*

**[Must] FR-15** — CRUD товарів. 🟡
→ *AC:* Admin/Moderator — будь-які товари; Seller — лише власні (`SellerId` береться з JWT, чужий товар → 403); зображення завантажуються в Cloudinary (`POST /api/images`, ліміт 5 МБ, повертається HTTPS URL); валідація DTO (`CreateAdminProductDto`, `CreateSellerProductDto` та ін.). *Видалення фізичне (soft delete / `IsDeleted` відсутні); поля «опис» і «кількість на складі» не реалізовані.*

**[Must] FR-16** — Управління замовленнями. 🟡
→ *AC:* Перегляд усіх замовлень (`GET /api/orders` — Admin/Moderator); зміна статусу `Pending → Paid → Shipped → Delivered / Cancelled` (`PUT /api/orders/{id}/status`); історія змін зберігається. *Сповіщення користувачеві при зміні статусу (email/SignalR) не реалізовані.*

**[Must] FR-17** — Управління користувачами. 🟡
→ *AC:* Список користувачів (Admin/Moderator); блокування/розблокування: Admin — будь-кого, крім адміністраторів; Moderator — крім адміністраторів і модераторів; зміна ролей за правилами FR-22; адмін-CRUD користувачів і гостей (`/api/admin/customers`, `/api/admin/guests`). *Причина блокування не зберігається (лише прапорець `IsBanned`).*

### 4.6. Особистий кабінет

**[Must] FR-18** — Редагування профілю. 🟡
→ *AC:* `/api/profile`: зміна імені, телефону (нормалізований формат, валідація), паролю (через email-підтвердження), email (дворівневий процес із підтвердженням, унікальність). *Не реалізовано: аватар, збережена адреса доставки в профілі.*

**[Should] FR-19** — Список обраного (Wishlist). ❌
→ *Відкладено; у коді відсутній.*

**[Could] FR-20** — Push-сповіщення про зміну статусу замовлення. ❌
→ *Відкладено. Каталоги `Hubs` та `SignalR` у backend порожні (заготовки). Клієнт визначає зміну ролі через періодичний ping `/api/session` (див. FR-28).*

### 4.7. Нові вимоги (додано у версії 1.1)

**[Should] FR-22** ➕ — Керування ролями. ✅
→ *AC:* Make Seller — Admin або Moderator; Make Moderator та Remove Moderator — лише Admin; Seller → Customer — Admin або Moderator; роль Admin через API присвоїти не можна; адміністраторів та (для Moderator) інших модераторів змінювати не можна; заблокований акаунт не підвищується.

**[Should] FR-23** ➕ — Заявки на статус продавця. ✅
→ *AC:* Customer подає заявку з повідомленням (≤ 500 символів); одна активна заявка (`Pending`) на користувача; заблоковані та вже продавці/співробітники подати заявку не можуть; Admin/Moderator схвалюють (`Approved` — роль стає Seller) або відхиляють (`Rejected`) з фіксацією рецензента й часу (`/api/seller-requests/...`); розгляд повторно неможливий.

**[Should] FR-24** ➕ — Двофакторна автентифікація через email. ✅
→ *AC:* Після пароля надсилається 6-значний код (життя 10 хв, до 5 спроб, повторна відправка не частіше ніж раз на 30 с); сесія видається лише після `POST /api/auth/login/verify-code`; Google-вхід 2FA не вимагає; вмикається `TwoFactor:Enabled` + налаштований SMTP (за відсутності SMTP 2FA вимикається з попередженням у логах).

**[Must] FR-25** ➕ — Refresh-токени з ротацією. ✅
→ *AC:* Refresh-токен — 64 випадкових байти, у БД зберігається лише SHA-256-хеш; термін життя `Jwt:RefreshTokenDays` (за замовчуванням 14 днів); при кожному оновленні токен ротується; повторне використання відкликаного токена відкликає всі сесії користувача; для заблокованих користувачів оновлення відхиляється; роль перечитується з БД.

**[Should] FR-26** ➕ — Синхронізація ролі між токеном і БД. ✅
→ *AC:* На кожному запиті роль із JWT порівнюється з поточною роллю користувача; при розбіжності запит відхиляється (401), клієнт розлогінює користувача; `GET /api/session` використовується клієнтом для швидкого виявлення зміни ролі.

**[Could] FR-27** ➕ — Гостьові сесії. 🟡
→ *AC:* Сервіс гостей (`IGuestService`) створює гостьові сесії з `SessionKey`; гості мають роль `Guest` і не можуть оцінювати товари чи оформлювати замовлення.

**[Should] FR-28** ➕ — Виробники (Manufacturers). ✅
→ *AC:* CRUD виробників в адмін-панелі; у формі товару виробник вибирається зі списку (у `Product` виробник зберігається як рядок).

**[Could] FR-29** ➕ — Відеокаталог (серіали, епізоди, жанри). 🟡
→ *AC:* CRUD серіалів, епізодів і жанрів (`/api/series`, `/api/episodes`, `/api/genres`); імпорт метаданих через OMDb (`/api/omdb`); сторінки `/movies`, `/movies/categories`, `/movies/title/:id`. *Модуль фільмів (`FilmService`, `FilmRepo`) закоментований у DI.*

**[Should] FR-30** ➕ — Багатомовний інтерфейс. ✅
→ *AC:* Мови en / ua / ru (перемикач у хедері; вибір зберігається в `localStorage`; атрибут `lang` документа та локаль дат/чисел відповідають мові); словник перекладів у `i18n/translations.js`.

## 5. Use Cases

### UC-01: Оформлення покупки

| | |
|---|---|
| **Актор** | Покупець (Customer) |
| **Передумови** | Користувач авторизований і не заблокований; товари в кошику |
| **Основний потік** | 1. Користувач переходить у кошик → 2. Перевіряє товари та кількість → 3. Натискає «Оформити замовлення» → 4. Вводить адресу доставки (країна, місто, вулиця) → 5. Система створює замовлення зі статусом `Pending` та фіксує ціни позицій → 6. Клієнт ініціює оплату (`/api/payments/create`) → 7. Підтверджується оплата (mock-провайдер) → 8. Замовлення переходить у `Paid`, кошик очищується, користувач бачить замовлення в історії |
| **Альтернативний потік** | 7a. Оплата відхилена → повідомлення про помилку, замовлення залишається `Pending`, можна повторити; 8a. До відправлення користувач скасовує замовлення (`Cancelled`) |
| **Постумови** | Замовлення збережено в Firestore зі статусом `Paid`; запис в історії статусів. *(Складські залишки не списуються — не реалізовано.)* |

### UC-02: Додавання товару (адміністратор, модератор або продавець)

| | |
|---|---|
| **Актор** | Admin / Moderator / Seller |
| **Передумови** | Актор авторизований з відповідною роллю |
| **Основний потік** | 1. Admin/Moderator: вхід у адмін-панель (`/admin`) → «Products» → «Add product»; Seller: сторінка `/sell` → 2. Заповнює форму (назва, ціна, знижена ціна, виробник, категорія) → 3. Завантажує зображення (Cloudinary, ≤ 5 МБ) → 4. Зберігає |
| **Альтернативний потік** | 3a. Файл завищеного розміру або недопустимого формату → помилка, збереження блокується; 4a. Seller намагається змінити чужий товар → 403 |
| **Постумови** | Товар доступний у каталозі; для Seller `SellerId` дорівнює id з JWT |

### UC-03: Блокування користувача

| | |
|---|---|
| **Актор** | Admin або Moderator |
| **Передумови** | Виявлено порушення (спам, шахрайство); ціль не є адміністратором (для модератора — також модератором) |
| **Основний потік** | 1. Актор відкриває вкладку «Users» → 2. Натискає «Ban» → 3. Система встановлює `IsBanned = true` |
| **Альтернативний потік** | 3a. Ціль — адміністратор/модератор → 403 з поясненням |
| **Постумови** | Користувач не проходить політики `NotBanned`, не може оновити refresh-токен; його існуючий access-токен втрачає доступ до захищених ендпоінтів. *Причина блокування та email-повідомлення не реалізовані.* |

### UC-04: Заявка на статус продавця

| | |
|---|---|
| **Актор** | Покупець; Admin / Moderator |
| **Передумови** | Покупець авторизований, не заблокований і має роль Customer; немає активної заявки |
| **Основний потік** | 1. Покупець надсилає заявку з повідомленням → 2. Заявка отримує статус `Pending` → 3. Admin/Moderator у вкладці «Seller requests» схвалює заявку → 4. Роль користувача змінюється на Seller → 5. Після наступного входу (або виявлення розбіжності ролі в токені) користувач бачить кабінет продавця |
| **Альтернативний потік** | 3a. Заявка відхиляється (`Rejected`) |
| **Постумови** | Заявка закрита з фіксацією рецензента (`ReviewedBy`) та часу |

### UC-05: Вхід з двофакторною автентифікацією

| | |
|---|---|
| **Актор** | Користувач із підтвердженим email |
| **Передумови** | Увімкнено `TwoFactor:Enabled` і налаштовано SMTP |
| **Основний потік** | 1. Користувач вводить email і пароль → 2. Система повертає `twoFactorRequired`, `challengeId`, `maskedEmail` → 3. Користувач вводить код з листа → 4. `POST /api/auth/login/verify-code` повертає access- і refresh-токени |
| **Альтернативний потік** | 3a. Код невірний — до 5 спроб, далі потрібен новий вхід; 3b. Код не надійшов — повторна відправка не раніше ніж через 30 с |
| **Постумови** | Видано пару токенів; створено запис refresh-токена (хеш) |
